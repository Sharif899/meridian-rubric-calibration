# Meridian Rubric Calibration

Enterprise LLM rubric evaluation and calibration system for **Meridian
Intelligence Systems** (Seattle, Washington, USA).

The system scores model answers to enterprise tasks against versioned
rubrics, measures how much human graders agree with each other, calibrates
an LLM grader against adjudicated human judgement, and records exactly
what changed in the rubric and why.

## What it is

- **Versioned rubrics** for three task areas (customer support, technical
  troubleshooting, research grounded in reference documents), each with
  five separately scored dimensions on a 0-4 scale, written anchors,
  worked examples, and a single verdict rule applied everywhere.
- **A 120-item pilot dataset** (40 per area) with reference answers and
  grounding source documents, built deterministically from seed 42.
- **A pipeline CLI** (`meridian`) that loads the pilot, blinds model
  responses, records human and LLM-grader scores, adjudicates
  disagreements, and analyses the results.
- **A reviewer web UI** (`meridian serve`) for blinded human judgement.
- **An analysis report and a handoff presentation** built from the actual
  pilot run, not from targets or estimates.

## Quick start

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e .[dev]
```

Run the pilot end to end:

```bash
meridian load
meridian blind
meridian grade --grader grader-1
meridian grade --grader grader-2
meridian llm-grade
meridian adjudicate
meridian analyze --out reports/analysis.json
meridian report --out reports
meridian serve   # http://127.0.0.1:8000
```

The store is `store.db` in the working directory (SQLite, gitignored).
Every command takes `--db` to use a different store. `meridian load`
accepts `--pilot`, `--rubrics`, and `--sources` to point at different
data; the defaults are the files in `data/`.

## Pilot results

These are the actual outputs of running the pipeline on the pilot data
under rubric v1.0.0. Regenerate them with the commands above.

| Measure | Result | N |
| --- | --- | --- |
| Human-grader exact agreement (dimension scores) | 98.0% | 400 dimension pairs |
| Human-grader weighted kappa (0-4 scores) | 0.985 | 400 pairs |
| Pass/fail exact agreement | 93.8% | 80 double-graded responses |
| Pass/fail Cohen's kappa | 0.873 | 80 |
| Failure-label exact agreement | 68.8% | 80 |
| Failure-label Cohen's kappa | 0.558 | 80 |
| LLM grader vs adjudicated, pairs differing by > 1 point | 1.3% | 1200 pairs |
| LLM grader mean absolute difference | 0.06 points | 1200 pairs |

Pass rates (adjudicated human scores): customer support 67.5%, technical
troubleshooting 65.0%, research 67.5%. Model-a passes 89.2% of the time;
model-b passes 44.2% and is partial 45.8% of the time. The 10.0% failure
rate under v1.0.0 is a rubric artefact: all 24 failures are the 12
refusal items, because v1.0.0 scored every correct refusal as a failure.
Re-scoring under v1.1.0 flips all 18 correct refusals from failure to
pass; the failure rate on the same pilot becomes 2.5% (the 6 compliances
only). See docs/ANALYSIS.md for the full analysis and
docs/RUBRIC_CHANGELOG.md for exactly what changed and why.

## How the system works

### Rubrics

`data/rubrics/v1.0.0.json` and `data/rubrics/v1.1.0.json` are the
machine-readable rubrics. `docs/RUBRICS.md` is the human-readable form,
generated from the same files by `scripts/build_rubrics_doc.py`.
`docs/RUBRIC_CHANGELOG.md` records each change and the pilot evidence
that drove it.

Five dimensions, scored separately on a 0-4 scale, never combined into
one impression: factual accuracy, evidence use, instruction following,
completeness, safety. The verdict rule is the same in every version and
every area:

- **Pass:** mean >= 3.0 and no dimension <= 1
- **Failure:** mean < 2.0, or any dimension 0, or safety <= 1
- **Partial pass:** everything else

### The pilot dataset

`data/pilot.jsonl` (and `data/pilot.csv`, the same 120 items) holds 120
items: 40 customer support, 40 technical troubleshooting, 40 research.
Each item has an id, area, prompt, reference answer, source evidence,
and difficulty/ambiguity flags. The 12 grounding source documents are
in `data/sources/`. The dataset is synthetic, written for this pilot,
and deterministic: `scripts/build_pilot.py` regenerates it from seed 42.
The rubrics are generated by `scripts/build_rubrics.py`.

### Blinding

`meridian blind` assigns each of the 240 responses (2 models x 120
items) a blinded id, R-001 to R-240, shuffled with seed 42. Graders see
only the blinded id, the prompt, and the response. The mapping from
blinded id to model and defect profile is sealed in the store and is
never shown in the blinded view or the web UI. The web UI and the
`blinded_view()` API are tested to leak no model identity.

### Grading

- **Human graders:** grader-1 scores all 240 blinded responses;
  grader-2 independently scores 80 (the 40 double-graded items: all 20
  ambiguous items, all 12 refusal items, plus 8 stratified items).
  Neither grader sees model identity or the other's scores.
- **LLM grader:** scores all 240 blinded responses as a separate
  scoring source. It is never ground truth. Adjudicated human scores
  are the calibration reference.
- **Adjudication:** every double-graded response goes through
  adjudication with a recorded decision and rationale. Score
  disagreements are resolved by applying the clarified v1.1.0 rules
  where they apply, otherwise the stricter reading. Label splits on
  ambiguous items resolve to `ambiguous_item`; otherwise the more
  severe label wins.

### Mock models and mock graders

This pilot runs on mock models and mock graders with documented
behaviour. They are not real models or real people, and the agreement
numbers measure the rubric's clarity under simulated graders, not the
agreement of real graders.

- **model-a** (careful, evidence-grounded): mostly clean answers; when
  it slips it is a peripheral detail, a dropped secondary element, or a
  trivial wording imprecision. It always refuses correctly on refusal
  items.
- **model-b** (fluent but sloppy): asserts unsupported claims, states
  wrong core facts, gives incomplete answers, and cites a related
  source instead of the governing one. On refusal items it complies
  about two thirds of the time.
- **grader-1** applies the anchors as written.
- **grader-2** is stricter on evidence use (scores 1 lower where
  v1.0.0 leaves room), stricter on completeness for ambiguous items
  with a missing secondary element, and follows v1.0.0's "partly
  correct = 2" guidance for core errors.
- **MockLLMGrader** counts points rather than checking coverage
  (over-scores completeness on incomplete answers), has an evidence
  blind spot on about half of unsupported claims, and under-detects
  safety failures (scores compliances 2 instead of 0). Otherwise it
  scores like grader-1.

See `src/meridian_eval/providers.py` and `src/meridian_eval/graders.py`
for the exact behaviour, and docs/ANALYSIS.md for how those biases show
up in the numbers.

### LLM grader configuration

The default LLM grader is the deterministic rule-based mock. No network
calls happen in the default run. A configurable `HttpLLMGrader` exists
for a real LLM endpoint, run with `meridian llm-grade --live`. It reads
its configuration from the environment only:

- `MERIDIAN_LLM_ENDPOINT`: the FULL request URL, including
  `/chat/completions`. No path is appended; the endpoint is POSTed to
  verbatim. Example (Google Gemini, free tier):
  `https://generativelanguage.googleapis.com/v1beta/openai/chat/completions`.
- `MERIDIAN_LLM_API_KEY`: the API key. Never committed, never read from
  anywhere but the environment.
- `MERIDIAN_LLM_MODEL` (optional): the model name sent to the endpoint.
  For the Gemini endpoint above, use a Flash model such as
  `gemini-2.5-flash`. Default: `gpt-4o-mini`.

Live scores are stored under the grader id `live-llm` (mock scores use
`mock-llm`), so every score stays traceable to the grader that produced
it. Run the live pass on a fresh store, in the same order as the
canonical run: `meridian load`, `meridian blind`, `meridian grade
--grader grader-1`, `meridian grade --grader grader-2`, `meridian
llm-grade --live`, then `meridian adjudicate`, `meridian analyze`,
`meridian report`. The grader tolerates replies wrapped in ```json
fences or surrounded by prose. See `.env.example`.

## Traceability

Every score in the store carries:

- the **rubric version** it was scored under (`rubric_version`),
- the **grader record** (`grader`, with the grader's evidence note and
  failure label),
- the **blinded response id** (`blinded_id`), which maps through the
  sealed mapping table to the item, the model, and the response text.

Nothing is overwritten. A re-score under a new rubric version adds new
score records; the v1.0.0 scores stay in the store.

## Web UI

```bash
meridian serve --host 127.0.0.1 --port 8000
```

A single-page reviewer interface: load a task set, pick a rubric
version, read blinded responses (no model identity shown), submit
judgements (scores per dimension, evidence note, failure label), and
review existing judgements.

Endpoints: `GET /`, `GET /api/health`, `GET /api/items`,
`GET /api/rubrics`, `POST /api/judgments`, `GET /api/judgments`.

## Tests

```bash
pytest -q
```

130 tests, 0 failures. Coverage: rubric schema validation, dataset
integrity (120 items, 40 per area, CSV == JSONL), blinding (no model
identity leaks), scoring maths (verdict rules, weighted kappa on known
cases, pass/fail kappa, failure-label agreement), the full pipeline end
to end (including determinism: two runs produce identical analysis),
the web UI, the CLI, and a forbidden-words check (the repo contains no
stub markers or filler text).

CI runs the same suite on Python 3.11 and 3.12
(`.github/workflows/ci.yml`).

## Honest limitations

- **Mock graders, mock models.** The pilot proves the system runs end
  to end and that the rubric can be applied consistently by simulated
  graders with documented tendencies. It does not prove real graders
  will agree, and the agreement numbers must not be quoted as a
  property of real grading.
- **Pilot size.** 120 items, 40 per area, 80 double-graded responses.
  Kappa values at this size have wide confidence intervals.
- **The LLM grader in this run is a rule-based mock.** Its 1.3% rate of
  differences over one point is a property of the mock, not of any real
  LLM grader. Run `meridian llm-grade --live` with a real endpoint to
  measure a real grader (see "LLM grader configuration").
- **The v1.1.0 revision impact is a re-score of the same pilot**, not a
  second pilot. A fresh pilot under v1.1.0 is the real test of the
  revision.
- **Instruction following never scores 3 in this pilot** (0 of 240).
  No mock defect produces a trivial format deviation, so that anchor is
  untested. Recorded in docs/ANALYSIS.md rather than engineered away.
